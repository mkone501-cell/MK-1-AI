# 要件整理とシステム設計

## 1. 今回の目的

経営者の基本窓口を「AI秘書」に一本化し、最初の部門として「AI広告事業部」を用意します。最初の案件は NORTH STAR BEANS のEC売上向上ですが、データはクライアントと案件を分け、後から別の顧客を追加できる形にします。

## 2. 役割

- **AI秘書**: 普通の日本語で依頼を受け、担当AIへ仕事を振り分け、結果を分かりやすくまとめます。
- **営業AI**: 見込み客、問い合わせ、提案、追客の案を扱います。
- **広告戦略AI**: 商品・競合・対象顧客を分析し、媒体、企画、予算の案を作ります。
- **制作AI**: 広告文章、投稿、画像案、動画台本、商品紹介を作ります。
- **広告運用AI**: 出稿、予算配分、停止、改善、比較テストの案を作ります。
- **分析AI**: 売上、広告費、クリック、購入、CPA、ROASを分析します。

## 3. 安全ルール

次の操作はAIが直接実行せず、必ず「提案 → 承認待ち → 経営者の判断 → 実行」の順に進めます。

1. 広告費を使う
2. 商品価格を変更する
3. 顧客へ重要なメッセージを送る
4. 契約を締結する
5. データを削除する
6. 外部へ公開する

Ver.0.1は外部サービスに接続していないため、承認後も実行はせず、判断履歴だけを保存します。

## 4. データ構造

ブラウザ内に次の情報をまとめて保存します。

- `clients`: クライアント
- `projects`: 案件
- `conversations`: AI秘書との会話
- `tasks`: AI担当への仕事
- `responses`: AI担当の回答
- `adPlans`: 広告案
- `approvals`: 承認待ちと判断
- `adMetrics`: 広告実績
- `salesMetrics`: 売上実績
- `auditLog`: 誰が、いつ、何を行ったかの履歴
- `settings`: 会社と代表者の設定

## 6. 将来の拡張方法

次の段階では、ブラウザ内保存をサーバーとデータベースに置き換え、利用者のログイン、権限、バックアップを追加します。Meta広告、Google広告、Shopifyなどはそれぞれ独立した「接続部品」として追加し、承認管理を必ず通すようにします。採用部・経理部などもAI担当と仕事の種類を追加することで広げます。

外部接続、有料サービス契約、本番公開、APIキーの登録は経営者の確認を得てから行います。

## 7. Phase 1 バックエンド

現在の画面は変更せず、同じサーバーの`POST /api/chat`を呼び出します。

- APIキーあり: バックエンドがOpenAI Responses APIと通信します。
- APIキーなし: バックエンドがデモ応答を返します。
- GitHub Pages: バックエンドが存在しないため、ブラウザ側の従来デモへ自動的に戻ります。

APIキーは`OPENAI_API_KEY`環境変数からのみ読み込みます。ブラウザへ返すレスポンス、ログ、ヘルスチェックには含めません。

バックエンドは将来の機能追加に備えて、次の責任を分離しています。

- `server/server.js`: HTTP受付、入力制限、レート制限、静的画面配信
- `server/mirai-service.js`: ミライの指示とOpenAI API通信
- `server/demo-mirai.js`: APIキー不要のデモ応答
- `server/approval-policy.js`: 承認が必要な操作の判定

Phase 1ではAIへ外部操作用ツールを一つも渡しません。将来ツールを追加する際も、読み取り専用ツールと実行ツールを分離し、実行ツールはサーバーに保存された承認記録が一致した場合だけ動かします。

## 8. Phase 2 井上さん専用ログイン

Phase 2では、有料の認証サービスを契約せずに検証できる、バックエンド側の単一オーナー認証を追加します。

- メールアドレスとパスワードハッシュはサーバー環境変数だけに保存します。
- 生のパスワード、セッションID、APIキーをブラウザのJavaScriptやlocalStorageへ保存しません。
- セッションCookieは`HttpOnly`、`SameSite=Strict`とし、本番HTTPSでは`Secure`属性を付けます。
- 状態を変更するAPIは、本人セッションに結び付いたCSRFトークンも確認します。
- 認証設定済みの場合、`/api/chat`は未ログイン利用者へ`401`を返します。
- 認証未設定の場合はデモだけを利用でき、OpenAI APIキーが存在しても有料API通信を無効化します。

将来追加する売上、EC、不動産、金融、会計などの非公開APIは、`requireOwner`認証を通過しなければデータを返さないよう統一します。

保護操作を実行する際は、ログイン済みオーナー、承認済み状態、承認者ID、本人セッションからの判断記録がすべて一致する必要があります。AIの文章やブラウザ内の表示だけでは承認として扱いません。

### Phase 2時点の制限

- セッションはサーバーのメモリ内にあり、再起動すると消えます。
- 複数サーバー間でセッションを共有できません。
- パスワード再設定、二要素認証、監査記録のデータベース保存は未実装です。
- HTTPSと安全な本番ホスティングは未設定です。

本番公開前に、永続データベース、HTTPS、バックアップ、セッション失効、二要素認証またはパスキーを追加します。
