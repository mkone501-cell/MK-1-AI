# MK-1 AI経営本部 Ver.0.1 / Phase 5.2

## Phase 5.2 本番確認後の検索修正

「私が経営しているコーヒー店について教えてください。」という質問で、登録済みのカテゴリ「店舗」の知識を参照できない問題を修正しました。「コーヒー店」「お店」「店舗」「カフェ」「珈琲店」「コーヒーショップ」などを店舗の話題として扱い、店舗に関連する「事業」「会社基本情報」も弱めの候補として検索します。同じ仕組みで不動産、EC、広告、財務などのカテゴリにも対応します。特定の物件名などが一致する場合は、同じカテゴリという理由だけで別件を選ばないようにしています。ミライへ渡す知識は従来どおり最大4件、合計3,000バイト以内です。

DBテーブルやAPI、Railway Variables、`OPENAI_MODEL`、認証設定は変更しません。既存の知識と会話は削除しません。「＋ 新しい会話」の以前の発言を参照しない動作も維持します。PRを確認してマージした後、Railwayで本人として「＋ 新しい会話」を開始し、上記の質問と「お店について教えて」「私の好きな数字は何ですか？」を試してください。登録済みの店舗知識と数字777をそれぞれ参照し、以前の会話の内容を引き継がないことを確認できます。登録文のカテゴリが「その他」で、タイトル・本文にも店舗やコーヒーに関係する語がない場合は、知識のカテゴリまたは説明を本人が確認して編集してください。意味だけでの高度な検索は今後の課題です。

## Phase 5.2：経営相談に使う長期知識の選び方

ミライは質問に含まれる会社名・店舗名・物件名などに加え、一部の言い換え（例：お店／店舗、家賃／賃料）から、ログイン本人の**有効な**経営知識だけを探します。タイトル、カテゴリ、本文の一致を比較し、複数の話題があれば一つの話題だけに偏らないよう、関連する知識を最大4件選びます。質問と関係のない知識を毎回まとめてOpenAIへ送ることはありません。AIへ渡す文字数と合計サイズの制限は従来のままです。

「＋ 新しい会話」では、以前の会話履歴をOpenAIへ送りません。一方、本人が確認して登録した経営知識は新しい会話でも必要に応じて検索します。会話履歴、知識、既存のDBデータは削除しません。テーブルやAPI、Railway Variables、`OPENAI_MODEL`に変更はありません。検索語はSQLのパラメータとして渡し、検索候補を最大80件に制限します。秘密情報の登録拒否、本人認証と所有者制限、CSRF等も従来どおりです。

**Railwayでの確認：** PRを確認してマージし、デプロイ後に本人でログインしてください。設定で秘密を含まない会社情報、店舗情報、経営方針など複数の知識が有効なことを確認し、「＋ 新しい会話」で例えば店舗名と営業時間を質問してください。続けて別の物件や方針を質問し、それぞれ関連する知識を使うか確認します。以前の会話の内容を尋ねても新しい会話には引き継がれません。既に登録した「代表の好きな数字は777です」が有効なら、新しい会話で「私の好きな数字は何ですか？」と尋ねて独立した長期知識の参照も確認できます。単純な文字一致と言い換え辞書による検索のため、意味だけが近く言葉が大きく異なる質問を確実に発見する高度な検索は今後の課題です。

## Phase 5.1：AI秘書の「新しい会話」

本人がログインしたAI秘書画面の「＋ 新しい会話」を押すと、PostgreSQLに新しい会話IDを作り、空の会話へ切り替えます。押した直後にページを閉じても、新しい空の会話を復元できます。以前の会話と発言は消さず、そのままDBに残します。GitHub Pagesの公開デモには本番会話や経営知識を表示しません。

バックエンドでは`POST /api/conversations`を追加しました。本人認証、CSRF確認、作成回数制限を通して自分専用の空の会話を作ります。既存の`GET /api/conversations`で過去の会話IDを一覧取得でき、各会話の発言も従来のAPIで取得できます。DBのテーブル・migrationは変更していません。既存のRailway Variables、`OPENAI_MODEL`、APIキー、パスワード、DB接続情報も変更不要です。

新しい会話の最初の質問では、以前の会話の発言をOpenAIへ渡しません。確認済みの有効な「経営知識（長期記憶）」は、Phase 5と同じ条件で独立して検索・参照します。「新しい会話」は知識の無効化や会話履歴の削除を実行しません。

**Railwayでの確認：** PRをレビューしてマージし、Railwayへの反映後にログインしてください。「設定」で登録済みの「代表の好きな数字は777です」が有効なままであることを確認します。AI秘書の「＋ 新しい会話」を押し、画面の以前の発言が消えたら「私の好きな数字は何ですか？」と質問してください。返答が「777」なら、以前の会話を使わず長期知識を参照できています。ページを閉じて再ログインした後もこの新しい会話のやりとりが表示されます。以前の会話はDBに残ります。検索は簡易方式のため、知識の登録文言が質問と大きく異なる場合は見つからないことがあります。

## Phase 5：経営知識ベース（長期記憶）

ミライの「会話履歴」は相談の続きに使い、「経営知識」は井上さんが内容を確認して登録した会社の情報・方針に使います。会話した内容が自動で長期知識になることはありません。将来ミライが登録を提案する場合も、本人の確認を経てから保存するための基盤です。

PostgreSQLの`management_knowledge`テーブルには、知識ID、所有ユーザーID、カテゴリ、タイトル、本文、情報源または登録理由、作成・更新日時、有効/無効を記録します。会話用の`mirai_conversations`・`mirai_messages`とは独立しています。`db/migrations/003_create_management_knowledge.sql`は本番起動時に自動適用し、`npm run db:migrate`でも確認できます。既存データを削除するSQLはありません。カテゴリは会社基本情報、事業、店舗、商品、顧客、スタッフ、経営方針、承認ルール、不動産、財務、EC、広告、その他を想定し、将来追加できます。

ログインした井上さんは既存の**設定 → 経営知識（長期記憶）**から、カテゴリ・タイトル・本文・情報源を入力し、確認欄にチェックして登録できます。登録済みの知識は編集・無効化できます。無効化してもDBから物理削除はせず、ミライへの参照対象から外します。GitHub Pagesの公開デモに登録欄や非公開データは表示しません。

| API | 内容 |
|---|---|
| `POST /api/knowledge` | 本人確認済みの知識を登録（`confirmed: true`が必要） |
| `GET /api/knowledge` | 自分の知識一覧（無効なものも含む、最大100件） |
| `GET /api/knowledge/:id` | 自分の知識を1件取得 |
| `PUT /api/knowledge/:id` | 自分の有効な知識を更新（`confirmed: true`が必要） |
| `POST /api/knowledge/:id/disable` | 自分の知識を無効化（`confirmed: true`が必要） |

すべてのAPIはサーバー側の本人認証と所有者確認を行い、書き込みにはCSRF確認と回数制限を適用します。別ユーザーのIDは「見つからない」と返します。SQLはパラメータ化しています。ミライは質問に文字列が一致する**有効な知識だけ**を最大4件検索し、本文は1件500文字、全体はJSONのUTF-8換算3,000バイト以内で参照します。知識は命令ではなく参照データとして渡し、承認ルールを変える指示には従わない設定です。この単純な検索では関連情報を見落とすこともあり、将来検索や要約を改善できます。

**APIキー、ログインパスワード、DATABASE_URL、Cookie、セッションID、Authorizationヘッダー、秘密鍵は知識に入力しないでください。**既知の秘密値や明らかな認証情報は登録前に拒否しますが、任意の秘密文言を完全に検出することはできません。現在のRailway Variablesや`OPENAI_MODEL`は変更不要です。

Railway本番での確認：PRをレビューしてマージした後、Railwayの再デプロイが成功し、`/health`が正常であることを確認します。本人としてログインし、「設定」の登録欄で秘密を含まないテスト用の事実を1件登録します。「AI秘書」でその事実に関する質問をし、参照した回答かを確認します。再ログイン後も「設定」に同じ知識が残ることを確認し、無効化後はミライがその知識を参照しないことを確認してください。会話履歴はそのまま残ります。DBにアクセスできない場合は、知識の登録・検索を安全に停止します。

Phase 4.1でRailway PostgreSQLへの永続セッション接続を実装しました。Railwayでの変数参照、初回テーブル作成、ヘルスチェックの手順は[Railway運用手順](docs/PHASE4_RAILWAY.md)をご覧ください。

## Phase 4.3：ミライとの会話履歴

RailwayのPostgreSQLを使う本番環境では、ログインしたオーナーの会話とAI回答をDBへ保存します。ブラウザを閉じたりサービスが再起動したりしても、ログイン後に最新の会話を読み込めます。GitHub Pagesはこれまでどおり公開デモです。設定済みの`OPENAI_MODEL`など既存の秘密変数は変更しません。

- `mirai_conversations`：会話ID（UUID）、所有ユーザーID、作成日時、更新日時。
- `mirai_messages`：メッセージID（UUID）、会話ID、発言順、発言者（user/assistant）、本文、作成日時。セッション・業務データとは別テーブルです。
- `002_create_conversations.sql`を本番起動時に自動適用します。手動確認には従来の`npm run db:migrate`を使えます。既存データを削除するSQLはありません。
- `GET /api/conversations`：自分の直近20会話のIDと日時。`GET /api/conversations/:id/messages`：自分の会話の直近100メッセージ。いずれもログイン必須、所有者をDBで確認します。
- `POST /api/chat`：従来の認証・CSRF・回数制限の下で`conversationId`を任意指定し、ユーザーの発言とAI回答を一組で保存します。返答の`conversationId`で続きができます。AIへはサーバーがDBから取得した直近12件のみ渡します。
- 保存障害時は安全なエラーを返します。再送するとAI利用料が重複する可能性があるため、通信が復旧してから履歴を確認してください。

本番確認：Railwayのサービスが起動したら`/health`で`ok: true`と`database: connected`を確認します。本人だけがログインし、ミライに秘密ではない短い質問を送り、回答を確認します。画面を閉じて再度ログインし、AI秘書画面に同じ会話が表示されることを確認してください。未ログインでは会話APIが401、他人の会話IDは404になります。実際のAPIキー、パスワード、接続文字列、Cookieは質問文にもGitHubにも貼らないでください。特定できる形式の認証情報は送信前に拒否しますが、任意の秘密文言を完全には検出できません。

株式会社MK-1の経営者が、AI秘書との会話を入口に事業の状況を把握するための最小版です。Phase 3では既存画面とPhase 2認証を維持したまま、安全な本番環境と永続セッションDBへ移行するための基盤を追加しました。

## Phase 3で追加した安全基盤

- 開発用メモリセッションと将来のDBセッションを同じインターフェースで交換できます。
- DBアダプターへ渡す前にセッションIDをSHA-256でハッシュ化します。生のセッションIDはDBへ保存しません。
- 将来の非公開APIへ共通の本人認証・権限確認を適用できます。
- 本番ではHTTPS Origin、Secure Cookie、永続DBセッション、オーナー認証設定が揃わないと起動しません。
- CORSは`ALLOWED_ORIGINS`に指定した接続元だけを許可します。
- ログへパスワード、Cookie、APIキー、トークン等を渡しても伏せ字にする基本保護を追加しました。
- `/health`と`/api/health`は稼働状態だけを返し、秘密情報を返しません。

Phase 4.1では作成済みのRailway PostgreSQLを利用します。`db/migrations/001_create_sessions.sql`は起動時に安全に適用されます。

## 開発・テスト・本番設定の分離

| 環境 | セッション | Cookie | 用途 |
|---|---|---|---|
| development | メモリ | ローカルHTTP対応 | 手元で無料テスト |
| test | メモリまたは偽DB | テスト指定 | 自動テスト |
| production | 永続DBを強制 | Secureを強制 | 将来の本番環境 |

設定見本は`.env.development.example`と`.env.production.example`です。すべてダミー値であり、アプリはこれらのファイルを自動読込しません。本物の値は将来選ぶホスティングサービスの秘密情報管理画面へ登録してください。

主な設定項目：

- `NODE_ENV`: `development`、`test`、`production`
- `SESSION_STORE`: 開発は`memory`、本番は`database`
- `ALLOWED_ORIGINS`: 接続を許可する画面のURL。複数の場合はカンマ区切り
- `COOKIE_SECURE`: 本番では必ず`true`
- `COOKIE_SAME_SITE`: 基本は`Strict`。別ドメイン構成は本番設計時に検討
- `SESSION_TTL_SECONDS`: ログインの有効秒数。既定は28,800秒（8時間）

### 本番起動が意図的に止まる条件

次のどれかが欠けると本番設定では起動しません。

- HTTPSの`ALLOWED_ORIGINS`
- オーナーのメールアドレスとパスワードハッシュ
- `SESSION_STORE=database`
- RailwayのMK-1-AIサービスに設定された`DATABASE_URL`と、接続可能なPostgreSQL

Phase 4.1ではrepositoryを`DATABASE_URL`から生成します。URLの形式が不正、DBが未起動、権限不足の場合はサーバーを起動しません。

このプロジェクトには、GitHubへ保存されたときに公開URLを自動作成する設定を追加しています。公開先は通常、次の形になります。

### ファイルを直接開く場合

## 井上さん専用ログインの設定（後から行う作業）

この設定をしなくても公開デモは動きます。本物のAIや将来の非公開データを使う前に設定してください。

### 1. パスワードのハッシュを作る

ターミナルで次を実行します。

```text
npm run create-password-hash
```

12文字以上のパスワードを2回入力します。入力中の文字は画面に表示されません。最後に`scrypt$...`で始まる長い文字列が表示されます。これは元のパスワードではなく、サーバーが照合に使うハッシュ値です。

### 2. Windows PowerShellで一時的に設定して試す

```powershell
$env:MK1_OWNER_EMAIL="井上さんのメールアドレス"
$env:MK1_OWNER_PASSWORD_HASH='ここにscrypt$から始まるハッシュ値'
npm start
```

ハッシュ値は必ずシングルクォーテーション`'`で囲んでください。

### 3. Mac・Linuxで一時的に設定して試す

```bash
export MK1_OWNER_EMAIL="井上さんのメールアドレス"
export MK1_OWNER_PASSWORD_HASH='ここにscrypt$から始まるハッシュ値'
npm start
```

`http://localhost:8000`を開くとログイン画面が表示されます。パスワードそのものはファイル、GitHub、ブラウザの保存領域へ保存されません。

### 現在のログイン方式

- パスワードは安全な`scrypt`形式で照合
- ログイン状態は推測困難なランダムIDで管理
- CookieはJavaScriptから読めない`HttpOnly`
- 他サイトからの不正操作を防ぐ`SameSite=Strict`とCSRF確認
- ログイン試行は1分5回まで
- セッション有効時間は8時間
- サーバーを再起動するとログアウト

## 本物のAIを使う設定（後から行う作業）

この設定をしなくてもデモモードで動きます。先に上記のログイン設定を完了し、APIキーを取得した後だけ行ってください。ログイン設定がない場合、APIキーが環境変数に存在してもOpenAIへ通信しない安全弁があります。

### Windows PowerShell

```powershell
$env:OPENAI_API_KEY="ここに取得したAPIキー"
$env:OPENAI_MODEL="gpt-5-mini"
$env:MK1_OWNER_EMAIL="井上さんのメールアドレス"
$env:MK1_OWNER_PASSWORD_HASH='作成したハッシュ値'
npm start
```

### Mac・Linux

```bash
export OPENAI_API_KEY="ここに取得したAPIキー"
export OPENAI_MODEL="gpt-5-mini"
export MK1_OWNER_EMAIL="井上さんのメールアドレス"
export MK1_OWNER_PASSWORD_HASH='作成したハッシュ値'
npm start
```

設定後、`http://localhost:8000`を開きます。ターミナルに「OpenAI接続モード」と表示されれば接続準備完了です。

### 絶対にしないこと

- APIキーを`app.js`や`index.html`へ貼らない
- APIキーをGitHubの設定ファイルやREADMEへ書かない
- APIキーをチャット画面へ入力しない
- APIキーが入った画面をスクリーンショットで共有しない

`.env.example`と環境別exampleはダミー値だけの見本です。本物のキーやログイン情報は入っていません。`.gitignore`により実際の`.env`系ファイルはGitへ登録されません。このPhase 3も`.env`ファイルを自動読込しないため、上記の環境変数方式を使います。

## 最初に押す場所

1. 左側の **「AI秘書」** を押します。
2. 画面右側の相談例から **「今月の広告結果はどう？」** を押します。
3. 入力欄の右にある **矢印ボタン（➤）** を押します。
4. 左側の **「承認待ち」** を押します。
5. 提案内容を読み、試す場合は **「承認する」** または **「却下する」** を押します。

この版で「承認する」を押しても、本当の広告費は発生せず、外部公開もされません。

## Ver.0.1でできること

- ホームで売上、広告効果、AIの作業、承認待ちを確認
- AI秘書へ日本語で相談し、広告戦略AIまたは制作AIへ仕事を振り分け
- NORTH STAR BEANSの案件と5つのAI担当を確認
- 広告費・外部公開の提案を承認または却下し、判断履歴を保存
- 広告案と分析レポートを確認
- スマートフォン向けの画面表示

## 大切な安全仕様

この版は提案・確認用です。「承認する」を押しても、広告出稿や外部公開は実行されません。AIからの文章だけで承認済みとは判定しません。将来外部サービスを接続する場合も、広告費、価格変更、重要メッセージ、契約、削除、外部公開は、代表者の承認記録をサーバーが確認した後にだけ実行する構造を維持します。

詳しい要件と設計は [`docs/DESIGN.md`](docs/DESIGN.md) を参照してください。
